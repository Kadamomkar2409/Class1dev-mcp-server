Class1Dev MCP Server • Phase 1 Overview Executive Summary & Strategic Context

1. Executive Summary

The Class1Dev MCP Server bridges enterprise AI coding assistants (such as Claude Desktop, Cursor, and NitroStudio) with Class1's proprietary cost-risk simulation engine and cloud-native Neon PostgreSQL persistence. It transforms AI infrastructure governance from an ex-post CI/CD bottleneck into an interactive, real-time feedback loop.

What It Is

A high-performance Model Context Protocol (MCP) server built with the official NitroStack SDK (@nitrostack/core) and TypeScript. It exposes 10 domain-specific tools allowing AI agents to simulate LLM cost trajectories, enforce budget caps, query policy verdicts, and manage an immutable governance ledger in Neon PostgreSQL.

Why It Matters

Generative AI applications frequently suffer catastrophic cloud cost overruns when prompt sizes expand or model tiers are upgraded without screening. By embedding Class1 directly into the developer's chat and IDE workflow, cost governance "shifts left," catching regressions prior to commit.

What Phase 1 Proves

Phase 1 proves that the real class1==0.1.0 PyPI package runs reliably within a secure subprocess sandbox, performs 120,000 Monte Carlo runs in ~1.8s, calculates tail-risk percentiles (P50/P90/P95), and persists structured audit records to Neon PostgreSQL across both STDIO and HTTP transports.

What Comes Next (Phase 2)

Deployment to NitroCloud with public HTTPS routing to enable remote ChatGPT integration, real GitHub PR webhook ingestion, spend calibration against live cloud provider invoices, and per-tenant authentication for multi-enterprise SaaS delivery.

2. The Problem and the Opportunity

Strategic Thesis & Market Hypothesis

Labelled Product Argument: The following problem statement and commercial opportunity represent an architectural and product value argument formulated for founder review, rather than an independently audited empirical market claim.

The Current State: Friction at the Pull Request Gate

Currently, Class1 operates primarily as a CLI tool and GitHub Action triggered during Pull Request (PR) review. While effective at blocking unbudgeted code from reaching production, PR-time gating creates operational friction:

  • Late Discovery: Developers only discover that an LLM model upgrade or prompt refactor breaches monthly budget limits after authoring, testing, and opening a PR.
  • Costly Rework Cycles: Redesigning prompts or falling back to smaller models after completing code development introduces cycle delays and developer frustration.
  • Siloed Governance: CI/CD log summaries are ephemeral and disconnect financial oversight from engineering task management.

The Opportunity: Shift-Left AI FinOps via Model Context Protocol

The Model Context Protocol (MCP), pioneered by Anthropic and adopted across the AI ecosystem, creates a universal standard for AI assistants to invoke external tools and context stores. Implementing an MCP server for Class1 introduces three core business advantages:

1. In-IDE Cost Awareness

Developers can ask Cursor or Claude: "What will this migration from gpt-4o-mini to claude-3-5-sonnet cost our team at 50,000 monthly active users?" and receive instant percentile risk bands before writing the first commit.

2. Immutable Governance Ledger

Every evaluation automatically generates a persistent, UUID-indexed record in Neon PostgreSQL, providing FinOps leaders with a complete historical audit trail of all model changes and budget policy decisions.

3. What Phase 1 Delivers: The 10 MCP Tools

In accordance with the PRD specification and enterprise presentation requirements, the server exposes 10 specialized MCP tools. Generic database terminology has been replaced with domain-explicit FinOps actions, ensuring LLM agents understand their exact financial and governance purpose.

Tool Name PRD Alias Functional Purpose & Capabilities Business Benefit & Audience
evaluate_pr_cost_risk estimate_pr_cost Executes the real Class1 takeoff engine on before/after code diffs. Performs 120,000 Monte Carlo runs to project P50/P80/P90/P95 monthly spend and issues policy verdicts (BLOCK, WARN, PASS, NO_BUDGET). Eliminates Cost Surprises: Enables developers & FinOps teams to quantify tail risk prior to code merging.
get_pr_governance_verdict get_cost_verdict Retrieves stored Class1 cost-risk forecast metrics, percentile distributions, budget cap thresholds, and official policy verdict by record UUID. Automated CI/CD Gating: Allows automated bots and engineering leads to verify compliance status.
log_budget_policy_override create_record Logs an authorized budget exception, manual PR waiver, or custom governance policy record in Neon PostgreSQL with structured JSONB metadata. Formalized Accountability: Gives FinOps Directors a defensible log of approved budget exceptions.
get_governance_record get_record Fetches an existing cost estimate, waiver, or audit record by UUID, enforcing strict multi-tenant namespace scoping. Audit Traceability: Compliance officers can retrieve exact historical records for quarterly spend audits.
list_governance_ledger list_records Returns a paginated list (limit, offset) of historical cost evaluations and policy decisions stored in Neon PostgreSQL. Portfolio Visibility: FinOps managers can review all team evaluations across past quarters.
update_governance_record update_record Updates description, approver sign-off, risk tier, or ticket references on an existing governance record in Neon PostgreSQL. Workflow Flexibility: Enables human-in-the-loop review teams to attach ticket approvals to records.
delete_governance_record delete_record Permanently purges a retracted governance record or temporary testing entry from the database with ownership verification. Ledger Maintenance: System administrators can clean test artifacts while preserving audit logs.
audit_pr_cost_history search_records Executes case-insensitive substring search across historical record titles and descriptions to identify past evaluations. Knowledge Discovery: Engineers can inspect past model upgrades across similar repository services.
get_finops_compliance_metrics get_database_stats Aggregates total record counts, storage volume, audit log counts, and mutation success/failure ratios from Neon PostgreSQL. Executive Telemetry: Engineering VPs can view high-level platform activity and policy breach rates.
get_service_health get_system_status Diagnostic probe returning real-time Neon PostgreSQL connection status, pool latency (ms), server uptime, and active transport mode. Operational Assurance: DevOps engineers can monitor service health and database availability.
Architecture Principle: Layered Separation of Concerns

All 10 MCP tools are implemented as lightweight presentation controllers in class1.tools.ts. Business logic, input validation, SQL query compilation, and subprocess lifecycle management reside entirely within dedicated singleton services (RecordService, HealthService, Class1EngineService). This guarantees zero code duplication and uniform multi-tenant isolation across all endpoints.

6. How to Use It: Step-by-Step Setup Guide

The server is fully functional and ready for local demonstration. Follow these exact steps to launch the server and execute verification suites from the terminal.

Step 1: Environment Setup

Ensure Node.js 22+ (v24.17.0 tested) and Python 3.11+ (v3.14.6 tested) are installed. Configure .env with placeholders: 

cd "E:/Nitrostack/Task Third/neon-mcp-server"
cp .env.example .env
# Edit .env with your Neon pooler URL & secret:
DATABASE_URL=postgresql://<user>:<password>@<neon_hostname>/neondb?sslmode=require
AUTH_SECRET=<YOUR_32_BYTE_HEX_SECRET>
MCP_TRANSPORT=stdio
CLASS1_TIMEOUT_MS=30000

Step 2: Python Engine, DDL & Build

Install dependencies, apply Neon migrations, populate baseline PR seed data, and compile TypeScript: 

# Virtual env & pinned Class1 package
python -m venv .venv
.\.venv\Scripts\pip install -r requirements-class1.txt

# Node install, DDL migrations, seed & build
npm install
npm run db:migrate && npm run db:seed
npm run build

Step 3: Dual Transport Modes Explained

Option A: Streamable HTTP Transport

Runs standard HTTP on port 3000. Strictly requires Authorization: Bearer <AUTH_SECRET> header on all calls. 

npm start
# Listening on: http://127.0.0.1:3000/mcp
Option B: STDIO Transport (Local Clients)

Communicates over process stdin and stdout. Bypasses HTTP sockets and header authentication barriers. 

set MCP_TRANSPORT=stdio
node dist/index.js

7. Connecting from NitroStudio (v1.4.22)

NitroStudio Authentication Diagnostic & Resolution

The HTTP 401 Issue: During its initial connection probe to http://127.0.0.1:3000/mcp, NitroStudio v1.4.22 sends zero Authorization headers, resulting in an expected HTTP 401 Unauthorized rejection. Rather than compromising security with insecure HTTP bypasses, STDIO mode provides native local IPC without HTTP authentication barriers.

To connect NitroStudio v1.4.22 to this project:

  1. Open NitroStudio and click Add Server → Select Other Project.
  2. Set Transport Type: STDIO.
  3. Configure execution parameters (note forward slashes in path):
    • Command: node • Arguments: "E:/Nitrostack/Task Third/neon-mcp-server/dist/index.js"
    • Working Directory: E:/Nitrostack/Task Third/neon-mcp-server
    • Environment Variables: MCP_TRANSPORT=stdio, DATABASE_URL=<YOUR_NEON_URL>, AUTH_SECRET=<YOUR_SECRET>, PYTHONUTF8=1
  4. Click Connect: Studio immediately discovers all 10 tools and renders interactive forms on the App Canvas.

10. Quality and Safety Safeguards in Phase 1

The implementation adheres to enterprise defense-in-depth engineering principles. Every security boundary has been verified through automated regression suites:

Security Safeguard Technical Implementation Verification Evidence & Result
Bearer Authentication Timing-safe Bearer token comparison using crypto.timingSafeEqual over SHA-256 digests on POST /mcp. Verified in tests/auth-and-error.test.ts; missing token returns HTTP 401; invalid token returns HTTP 403.
Rate Limiting Protection Sliding-window in-memory limiter capping callers at 60 req/min on /mcp. Public health probe is exempt. Verified in scripts/test_edge_cases.mjs; request #40 during burst returns HTTP 429; GET /health returns 200.
Payload Size Ceiling Express body parser enforces strict 1 MB ceiling (express.json({ limit: '1mb' })). Verified in test_edge_cases.mjs Case 7; oversized payload immediately rejected with HTTP 413 Payload Too Large.
Sanitized Error Boundary Global error handler catches unhandled exceptions, masking database connection strings, passwords, and server paths. Deep unwrapping prevents [object Object] serialization; verified 0 unmasked secrets across 53 repository files.
Immutable Audit Logging Every tool execution, read, mutation, validation failure, and engine timeout writes to Neon audit_logs table. Verified in scripts/test_trigger_failures_audit.mjs; failure rows recorded with structured metadata.
Multi-Tenant Scoping The userId parameter acts as a logical namespace partition within the shared trust domain. Verified in scripts/test_tenant_isolation_http.mjs; User A cannot access, mutate, or delete User B's records.
Test Suite Coverage 42 Vitest unit tests across 3 suites; 7 live verification scripts covering transports, edge cases, and cold restarts. 42 of 42 unit tests passed; all 7 verification scripts passed; zero credentials leaked in scanner audit.

11. Honest Limitations of the Phase 1 Implementation

In accordance with engineering transparency, the following technical limitations apply to the Phase 1 release:

Limitation Area Current Phase 1 Reality Engineering Impact & Mitigation
Estimate Accuracy Class Output is strictly Class 5 (Screening Grade), with an accuracy range of -50% to +100%. Uncalibrated against actual customer production logs; suitable for relative risk screening, not accounting invoices.
Static Model Pricing Data The bundled model pricing snapshot is ~159 days old, pinned inside the upstream package. Recent LLM provider price cuts are not reflected; Phase 2 will introduce dynamic price catalog refreshes.
Upstream Packaging Defect #1 The class1==0.1.0 PyPI distribution omits the cost_engine/footprint.py module. Clean repository wrapper stubs all 14 names, disclaiming: "Ecological footprint: NOT COMPUTED"; zero fake metrics emitted.
Upstream Packaging Defect #2 37 upstream test files in class1 sdist import unbundled modules (autobuild, blue_book.prices). Pytest cannot collect these 37 files; core cost engine tests pass (430 of 439 collectable tests pass).
Policy Verdict Boundary The 80% WARN threshold is evaluated in our TypeScript server code. Does not utilize Class1's proprietary licensed gate binary; policy logic matches PRD mathematical formula.
Single Trust Domain Auth The server uses a single shared Bearer token (AUTH_SECRET) for the HTTP endpoint. Tenant isolation is by namespace selector (userId), not per-user cryptographic authentication.
Local PoC Scope Server is not connected to live GitHub PR webhooks and is not hosted on NitroCloud. Diffs must be passed as string parameters; Phase 2 will automate live pull request fetching.

12. Phase 2 Strategic Roadmap

Phase 1 proves the viability of the Class1 MCP architecture. Phase 2 transitions this proof-of-concept into a cloud-hosted, enterprise-ready FinOps platform:

Milestone 1: NitroCloud Edge Deployment

Deploy the containerized MCP server to NitroCloud with automated TLS certificate management, global edge routing, and public endpoint exposure (https://mcp.class1.dev/mcp).

Milestone 2: Remote ChatGPT Client Integration

Register the public Streamable HTTP endpoint in OpenAI ChatGPT as an authorized remote MCP application, enabling browser-based chat access for non-technical executives.

Milestone 3: Automated GitHub PR Webhook Ingestion

Integrate GitHub webhooks to automatically extract before/after AST code diffs upon PR creation, posting the Class1 risk forecast and verdict directly into PR comments.

Milestone 4: Cloud Spend Calibration Engine

Ingest historical cloud billing data (OpenAI, Anthropic, AWS Bedrock) to calibrate Monte Carlo probability distributions, upgrading estimates from Class 5 to Class 3/2 accuracy.

Milestone 5: Dynamic Price Catalog & Per-Repo Budgets

Implement automated daily model price scraping and multi-tier budget policies configured on a per-repository and per-organization basis.

Milestone 6: Per-Tenant OAuth2 / OIDC Authentication

Transition from a single shared secret to enterprise identity providers (Okta, GitHub OAuth, Auth0) for cryptographic multi-tenant data segregation.
